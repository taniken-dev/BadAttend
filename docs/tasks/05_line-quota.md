# タスク05：LINE の通数削減と使用状況の見える化

> 共通ルール（Next.js ドキュメントの確認、SQL の置き場所、時刻の扱い、コミット方法）は [README.md](README.md) を参照。

## 背景

- LINE Messaging API の無料枠（コミュニケーションプラン）は**月200通**。今は半月ほどで使い切ってしまう。
- **通数は「受け取った人数」で数えられる。** グループ宛てに1回送ると、グループの人数分を消費する（[LINE Developers：通数カウント方法](https://developers.line.biz/ja/tips/2026/05/28/how-to-count-messages/)）。
- アプリの通知先グループ（`LINE_GROUP_ID`）には**部員全体（50人以上）がいる**。当日欠席の自動通知が1回あるたびに、50通以上を消費している。**これが一番の原因と考えられる。**
- 方針：
  - 個人への送信はやめる
  - 締切のお知らせは、アプリが作った文章を人が貼る方式にする（タスク04で対応済み）

## アプリが LINE に送っている箇所

| 箇所 | 送り先 | 1回あたりの通数 | 扱うタスク |
|------|--------|----------------|-----------|
| `src/app/api/line/group-notify/route.ts` | グループ（当日欠席・当日遅刻・事前欠席の自動通知） | **グループの人数（50人以上）** | **05** |
| `src/app/api/cron/remind/route.ts` | 未提出者（個別の multicast） | 未提出者の人数 | 04（廃止） |
| `src/app/api/line/notify/route.ts` | 未提出者（管理者のボタン操作・multicast） | 未提出者の人数 | 04（コピー用の文章に置き換え） |
| `src/app/api/cron/deadlines/route.ts` | 管理者と幹部（体育会書類の締切・multicast） | 管理者と幹部の人数 × 回数 | **05** |

## 要件

### 1. 使用状況の見える化（先にやる）

- 管理者画面（`/admin/members` の上部、または設定メニュー）に、**今月の送信数と上限**を表示する。
  - 使う API：`GET https://api.line.me/v2/bot/message/quota`（上限）と `GET https://api.line.me/v2/bot/message/quota/consumption`（今月の使用数）
  - 仕様は [LINE Developers](https://developers.line.biz/ja/reference/messaging-api/) で確認する。
- 残りが少ない（例：残り20%以下）ときは警告色で表示する。

### 2. グループへの自動通知の見直し（⚠️ 実装前にユーザーに確認する）

`group-notify` は、当日欠席などが1件あるたびにグループの人数分を消費する。次の案をユーザーに提示して選んでもらう。

| 案 | 内容 | 通数 |
|----|------|------|
| A. コピー用の文章に置き換える | アプリの「今日の欠席・遅刻連絡」一覧から、コピー用の文章を作る。管理者やマネージャーが貼る | 0 |
| B. まとめて1回だけ送る | 当日分をまとめ、練習開始の◯時間前に1回だけグループに送る（cron） | 練習1回あたりグループ人数 × 1 |
| C. 通知先を少人数のグループに変える | 幹部・マネージャーだけのグループを作り、そこに送る（`LINE_GROUP_ID` を差し替える） | その人数 × 件数 |
| D. 残数で自動的に止める | 1の使用数を確認し、残りが一定以下なら送らない（アプリ内の表示だけにする） | 可変 |

- 組み合わせてもよい（例：C + D）。
- 同じ理由で、事前欠席の通知を残すかも確認する。

### 3. 体育会書類の締切通知（`cron/deadlines`）

- 管理者と幹部への個別送信になっている。人数は少ないが「個人への送信はやめる」方針に含めるか、ユーザーに確認する。
- やめる場合：ホーム画面の締切カード（`DeadlineSection.tsx`）で十分に気づけるか検討する。取得失敗などの異常通知だけは残す案も提示する。

### 4. 送信の記録（任意）

- どの機能が何通使ったかを後から追えるように、`line_send_logs`（種別、宛先の種類、推定通数、日時）を記録する案を検討する。1の API で合計は取れるので、必須ではない。
